# Optimization Engine — Engineering Design Document

## 1. Overview

The optimization engine transforms the meal plan regeneration feature from a deterministic single-plan generator into a multi-candidate optimization system.

Instead of generating one weekly plan and returning it, the engine:

1. Generates **N independent candidate plans** (default: 10) using the existing generation pipeline with different random seeds.
2. **Scores** each candidate against multiple criteria (macro accuracy, diversity).
3. **Selects** the highest-ranked candidate (lowest score wins).
4. Returns only the winning plan to the UI.

This architecture **extends** the existing system. The original generation pipeline (`generateWeeklyMealPlan`) is preserved unchanged. The optimization layer wraps it with a candidate-generation, scoring, and selection pipeline.

**Key goal:** Every click on "Regenerate" produces a genuinely different and potentially better plan, while remaining deterministic and reproducible.

## 2. Architecture

### Production Flow

```
NutritionTabContent.tsx
  → optimizationEngine.generate()
    → CandidateGenerator.generateCandidates()
      → generateWeeklyMealPlan()
        → existing meal-plan generation pipeline
    → PlanScorer.score()
    → PlanSelector.selectBest()
```

### Component Responsibilities

| Component | Responsibility |
|-----------|----------------|
| **NutritionTabContent** | UI layer. Owns `regenerationCount` (via `useRef`). Calls `optimizationEngine.generate()` and passes `result.plan` to `setDraftPlan()`. |
| **OptimizationEngine** | Stateless orchestrator. Composes generator, scorer, and selector. No logic beyond pipeline coordination. |
| **CandidateGenerator** | Produces N independent candidate plans. Each candidate uses a unique seed derived from `(clientId, regenerationCount, candidateIndex)`. Delegates actual generation to `generateWeeklyMealPlan()`. |
| **PlanScorer** | Evaluates a single candidate against configured criteria. Returns a weighted total score and breakdown. Pure and read-only. |
| **PlanSelector** | Selects the best candidate from a scored population. Returns the candidate with the lowest total score. Tie-break: lowest `candidateIndex`. |

### Module Structure

```
src/services/optimization/
  ├── types.ts                    # Interfaces and contracts
  ├── seedFactory.ts              # Deterministic seed derivation
  ├── CandidateGenerator.ts       # Multi-candidate generation
  ├── PlanScorer.ts               # Criterion-based scoring
  ├── PlanSelector.ts             # Best-candidate selection
  ├── OptimizationEngine.ts       # Orchestration + factory
  └── *.test.ts                   # Unit tests
```

## 3. Design Principles

### Architectural Invariants

These rules must be preserved by all contributors:

1. **`WeeklyMealPlanResult` remains the canonical plan model.**
   - The optimization layer does not introduce a parallel plan representation.
   - All UI components, snapshots, and persistence layers continue to work with `WeeklyMealPlanResult`.

2. **No parallel meal-plan generation pipeline exists.**
   - `generateWeeklyMealPlan()` is the single source of truth for plan generation.
   - The optimization layer wraps it; it does not replace it.

3. **`CandidateGenerator` never mutates inputs.**
   - `GenerationInput` is treated as immutable.
   - Each candidate is produced independently.

4. **`PlanScorer` is pure and read-only.**
   - Scoring reads from `CandidatePlan` and `ScoringContext` without mutation.
   - No side effects, no I/O, no global state.

5. **`PlanSelector` is deterministic.**
   - Given the same scored candidates, always returns the same winner.
   - Tie-breaking is explicit and reproducible.

6. **`OptimizationEngine` owns no mutable state.**
   - All state (e.g., `regenerationCount`) lives in the caller (UI).
   - The engine is a pure function of its input.

7. **UI owns `regenerationCount`.**
   - The UI increments the counter before each generation.
   - The engine does not track or modify regeneration state.

8. **All optimization is deterministic for identical inputs.**
   - Same `(clientId, likedFoods, macroTargets, regenerationCount, candidateCount)` → identical seeds, plans, scores, and winner.

### Why These Invariants Exist

- **Determinism** enables reproducible results for coaches and reliable testing.
- **Single generation pipeline** avoids divergence between optimized and non-optimized paths.
- **Read-only scoring** ensures criteria can be added/removed without side effects.
- **Stateless engine** simplifies reasoning, testing, and future algorithm swaps.
- **Canonical plan model** ensures UI, snapshots, and persistence remain untouched.

## 4. Candidate Generation

### Seeded Generation

Each candidate plan is generated by calling the existing `generateWeeklyMealPlan(likedFoods, macroTargets, seed)` with a unique seed.

The seed is derived deterministically:

```typescript
`plan-${clientId}-${regenerationCount}-candidate-${candidateIndex}`
```

### Key Concepts

| Concept | Purpose |
|---------|---------|
| **`clientId`** | Namespaces the seed space. Different clients never share seeds. |
| **`regenerationCount`** | Increments on each regeneration click. Ensures each click produces a fresh candidate population. |
| **`candidateIndex`** | Unique identifier within a population (0 to N-1). Ensures each candidate in a single generation gets a different seed. |
| **`candidateCount`** | Number of candidates to generate (MVP default: 10). Configurable per call. |

### Determinism Contract

- **Same inputs** → identical candidate population.
- **Different `candidateIndex`** → different seed → different plan.
- **Different `regenerationCount`** → different seed population → different candidates.
- **Different `clientId`** → different seed namespace → different candidates.

### Regeneration Behavior

1. User clicks "Regenerate".
2. UI increments `regenerationCountRef.current`.
3. UI calls `optimizationEngine.generate({ ..., regenerationCount, candidateCount })`.
4. Engine generates N candidates with seeds derived from the new `regenerationCount`.
5. Engine scores and selects the best candidate.
6. UI receives the winning `CandidatePlan` and passes `result.plan` to `setDraftPlan()`.

**Guarantee:** The engine never intentionally regenerates the exact previous plan because `regenerationCount` always increments.

## 5. Scoring System

### Macro Accuracy Criterion

**Purpose:** Measures how closely the plan matches the target macros.

**Implementation:**
- Reads pre-computed `weeklyVariance` and `weeklyTargetMacros` from the plan.
- Computes absolute percentage variance for each macro: `|actual| / target`.
- Sums variances for calories, protein, carbs, and fat.
- **No recomputation** — uses existing variance data.

**Weight:** `1.0` (default)

**Lower is better.** A perfect plan scores `0`.

### Diversity Criterion

**Purpose:** Penalizes repetitive plans that reuse the same recipes, ingredients, or meal structure.

**Implementation:**
- **Repeated recipes:** Counts excess occurrences of identical `recipeText` across all meals.
- **Repeated ingredient combinations:** Counts excess occurrences of identical ingredient-ID sets across meals.
- **Repeated meal structure:** Counts excess occurrences of the same protein in the same meal slot across days.

Normalizes by total meal count (28 meals per week).

**Weight:** `0.3` (default)

**Lower is better.** A fully diverse week scores `0`.

### Weighting

Total score = Σ (criterion.rawScore × criterion.weight)

Weights are configurable via `ScoringConfig`. The default configuration includes:
- `macroAccuracyCriterion` (weight: 1.0)
- `diversityCriterion` (weight: 0.3)

### Adding a New Scoring Criterion

To add a new criterion without modifying the engine:

1. Implement the `ScoringCriterion` interface:

```typescript
const myCriterion: ScoringCriterion = {
  id: 'my-criterion',
  weight: 0.5,
  score: (candidate, context) => {
    // Return a numeric score (lower = better)
    return computeScore(candidate.plan);
  },
};
```

2. Add it to the scoring config:

```typescript
const config: ScoringConfig = {
  criteria: [
    macroAccuracyCriterion,
    diversityCriterion,
    myCriterion,
  ],
};
```

3. Pass the config to `PlanScorer`:

```typescript
const scorer = new PlanScorer(config);
```

**No changes to `OptimizationEngine`, `CandidateGenerator`, or `PlanSelector` are needed.**

## 6. Selection

### Selection Rule

The `PlanSelector` returns the `CandidatePlan` with the **lowest total score**.

### Tie-Breaking

If multiple candidates have identical `score.total`, the selector chooses the one with the **lowest `candidateIndex`**.

### Why Deterministic Selection Matters

- **Reproducibility:** Coaches can trust that the same inputs always produce the same plan.
- **Testability:** Tests can assert exact winners without mocking randomness.
- **Debuggability:** Deterministic selection simplifies tracing why a particular plan was chosen.

## 7. Extension Points

The optimization engine is designed for future algorithm swaps. Three extension points exist:

### CandidateGenerator

**Interface:**
```typescript
interface CandidateGenerator {
  generateCandidates(input: GenerationInput): CandidatePlan[];
}
```

**Current implementation:** `SeededCandidateGenerator` — generates N independent candidates with different seeds.

**Future algorithms:**
- **Genetic Algorithm:** Generate an initial population, then evolve candidates through crossover and mutation over multiple generations.
- **Simulated Annealing:** Start with one candidate and iteratively perturb it, accepting worse candidates with decreasing probability.
- **Beam Search:** Generate candidates breadth-first, keeping only the top-K at each step.
- **Monte Carlo:** Generate random candidates and select the best.

**How to plug in:** Implement `CandidateGenerator` and pass it to `OptimizationEngine` via `OptimizationEngineConfig`.

### PlanScorer

**Interface:**
```typescript
interface PlanScorer {
  score(plan: CandidatePlan, context: ScoringContext): PlanScore;
}
```

**Current implementation:** `PlanScorer` with `macroAccuracyCriterion` and `diversityCriterion`.

**Future criteria:**
- **Cuisine variety:** Penalize repeated cuisine types.
- **Seasonal ingredients:** Reward seasonal ingredients.
- **Budget optimization:** Penalize expensive ingredients.
- **Micronutrient balance:** Score vitamin/mineral coverage.
- **User preference learning:** Weight ingredients based on historical preferences.

**How to plug in:** Add new `ScoringCriterion` objects to `ScoringConfig.criteria`.

### PlanSelector

**Interface:**
```typescript
interface PlanSelector {
  selectBest(scoredCandidates: ScoredCandidate[]): CandidatePlan;
}
```

**Current implementation:** `PlanSelector` — selects the candidate with the lowest total score, tie-breaking by `candidateIndex`.

**Future algorithms:**
- **Tournament selection:** Randomly sample K candidates and select the best.
- **Roulette wheel selection:** Select candidates proportional to fitness.
- **Elitism:** Always preserve the top-E candidates.

**How to plug in:** Implement `PlanSelector` and pass it to `OptimizationEngine` via `OptimizationEngineConfig`.

### Example: Genetic Algorithm Integration

```typescript
class GeneticCandidateGenerator implements CandidateGenerator {
  generateCandidates(input: GenerationInput): CandidatePlan[] {
    // 1. Generate initial population (delegate to SeededCandidateGenerator)
    // 2. Evaluate fitness (delegate to PlanScorer)
    // 3. Select parents (tournament/roulette)
    // 4. Crossover and mutate
    // 5. Repeat for N generations
    // 6. Return final population
  }
}

const engine = new OptimizationEngine({
  generator: new GeneticCandidateGenerator(),
  scorer: new PlanScorer(createDefaultScoringConfig()),
  selector: new PlanSelector(),
});
```

**No changes to `OptimizationEngine` required.**

## 8. Performance

### Complexity

| Operation | Complexity | Notes |
|-----------|------------|-------|
| Candidate generation | O(n) | n calls to `generateWeeklyMealPlan()` — each is O(1) for fixed 7-day structure |
| Scoring (macro) | O(n) | Reads pre-computed variance |
| Scoring (diversity) | O(n × 28) | 28 meals per week, linear scans |
| Selection | O(n) | Single linear scan with tie-break |
| **Total** | **O(n)** | n = `candidateCount` |

### MVP Performance

- **Typical `candidateCount`:** 10
- **Total operations:** ~280 recipe generations (10 candidates × 28 meals), ~280 score computations, 1 selection scan.
- **Expected runtime:** < 1 second on modern hardware (all in-memory, no I/O).

### Why This Is Acceptable

- Generation is **CPU-bound** but lightweight (pure in-memory calculations).
- No network calls, no database queries, no LLM inference.
- 10× generation cost is acceptable for a "Regenerate" button that produces a genuinely better plan.
- The UI shows a loading state during generation.

### Future Optimizations (Not Needed for MVP)

- **Parallel generation:** Could use `Promise.all()` with worker threads, but generation is CPU-bound, not IO-bound, so threading provides limited benefit in JavaScript.
- **Caching:** Could cache ingredient ID lookups, but maps are small (~112 lookups total).
- **Incremental scoring:** Could score candidates as they generate and early-exit if a candidate is clearly worse, but scoring is already O(n) and fast.

### Unit Tests

The optimization module includes comprehensive unit tests:

| Test File | Tests | Coverage |
|-----------|-------|----------|
| `seedFactory.test.ts` | 9 | Seed derivation, uniqueness, determinism |
| `CandidateGenerator.test.ts` | 9 | Candidate count, seed uniqueness, determinism, plan diversity |
| `PlanScorer.test.ts` | 9 | Macro accuracy, diversity, criterion weighting, determinism |
| `PlanSelector.test.ts` | 6 | Lowest score selection, tie-breaking, order independence, empty input |
| `OptimizationEngine.test.ts` | 6 | Orchestration, generator/scorer/selector interaction, determinism |

**Total: 39 unit tests**

### Verified Properties

- **Deterministic generation:** Same inputs → identical candidate population.
- **Deterministic scoring:** Same plan + config → identical score.
- **Deterministic selection:** Same scored candidates → identical winner.
- **Candidate isolation:** Generating candidate A does not influence candidate B.
- **Edge cases:** Empty input, single candidate, large candidate count.
- **Integration wiring:** Engine is called correctly from UI, result flows to `setDraftPlan()`.

### Test Strategy

- **Mock-based tests:** `OptimizationEngine.test.ts` uses mock generator/scorer/selector to verify orchestration independently of recipe generation.
- **Fixture-based tests:** `PlanScorer.test.ts` and `CandidateGenerator.test.ts` use fixtures to construct deterministic plans.
- **Property-based tests:** Determinism is verified by running the same operation twice and asserting equality.

## 10. Future Improvements

These are **future work** and not part of the MVP:

### Scoring Enhancements

- **Configurable scoring weights:** Expose weights to coaches via UI.
- **User preference learning:** Learn ingredient preferences from historical selections and weight them in scoring.
- **Seasonal ingredient weighting:** Reward seasonal ingredients for freshness and cost.
- **Cuisine variety scoring:** Penalize repeated cuisine types (e.g., Italian three nights in a row).
- **Budget optimization:** Penalize expensive ingredients or optimize for cost.
- **Micronutrient optimization:** Score vitamin and mineral coverage, not just macros.

### Algorithm Enhancements

- **Genetic Algorithm:** Evolve candidates through crossover and mutation.
- **Simulated Annealing:** Iteratively improve a single candidate with probabilistic acceptance of worse solutions.
- **Beam Search:** Breadth-first search with pruning to explore more candidates efficiently.
- **Monte Carlo Tree Search:** Explore promising candidate regions more deeply.
- **ML-based ranking:** Train a model to predict coach preferences and use it as an additional scoring criterion.

### Performance Enhancements

- **Parallel candidate generation:** Use worker threads if runtime supports it.
- **Incremental scoring:** Score candidates as they generate and early-exit if clearly suboptimal.
- **Candidate caching:** Cache generated candidates for identical inputs (if regenerationCount is reset).

### UI Enhancements

- **Scoring transparency:** Show coaches why a plan was selected (macro accuracy score, diversity score).
- **Manual override:** Allow coaches to lock a specific candidate before selection.
- **Regeneration history:** Show previous regenerations and their scores.

## 11. Architectural Guarantees

Future contributors must preserve the following guarantees:

1. **Do not replace `generateWeeklyMealPlan()`.**
   - It is the single source of truth for plan generation.
   - The optimization layer wraps it; it does not replace it.

2. **Do not introduce a second generation pipeline.**
   - All plan generation must flow through `generateWeeklyMealPlan()`.
   - Parallel pipelines will cause divergence and bugs.

3. **Do not introduce a second plan model.**
   - `WeeklyMealPlanResult` is the canonical plan object.
   - All UI components, snapshots, and persistence layers depend on it.

4. **Keep the optimization engine stateless.**
   - `OptimizationEngine` must not own mutable state.
   - All state (e.g., `regenerationCount`) must live in the caller.

5. **Keep scoring deterministic.**
   - Same plan + same config → same score.
   - No hidden state, no randomness, no side effects.

6. **Keep selection deterministic.**
   - Same scored candidates → same winner.
   - Tie-breaking must be explicit and reproducible.

7. **Preserve `WeeklyMealPlanResult` as the canonical plan object.**
   - Do not introduce wrapper types or parallel representations.
   - The UI must continue to receive `WeeklyMealPlanResult` unchanged.

8. **New optimization algorithms should implement the existing interfaces instead of modifying the engine.**
   - Implement `CandidateGenerator`, `PlanScorer`, or `PlanSelector`.
   - Pass new implementations to `OptimizationEngine` via `OptimizationEngineConfig`.
   - Do not modify `OptimizationEngine.generate()`.

## Appendix: Key Types

```typescript
// Input to the optimization engine
interface GenerationInput {
  clientId: string;
  likedFoods: string[];
  macroTargets: MacroTargets;
  regenerationCount: number;
  candidateCount: number;
}

// A generated plan with metadata
interface CandidatePlan {
  plan: WeeklyMealPlanResult;
  seed: string;
  candidateIndex: number;
}

// Scoring result
interface PlanScore {
  total: number;
  breakdown: Record<string, number>;
}

// A candidate paired with its score
interface ScoredCandidate {
  plan: CandidatePlan;
  score: PlanScore;
}

// Engine configuration
interface OptimizationEngineConfig {
  generator: CandidateGenerator;
  scorer: PlanScorer;
  selector: PlanSelector;
}
```
